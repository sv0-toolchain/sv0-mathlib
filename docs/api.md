### `abs_checked_i64`

```sv0

```

Checked absolute value for i64: None only at i64::MIN, where abs_i64
would violate its own requires clause. BUGS.md #8 (enum payload slots
always a 32-bit `int`) is fixed upstream, but returns OptionI64, a
concrete companion to the shared prelude::Option<T> — NOT Option<i64> —
because sv0 generics resolve without monomorphizing (BUGS.md #9): the
shared Option<T>'s payload slot type is textually "T" at its
declaration, never a concrete type, so bug #8's per-slot-category
resolution has nothing to key off for the generic case. See BUGS.md #9
and docs/deviations.md.

### `abs_f64`

```sv0
fn abs_f64(x: f64) -> f64
    ensures(result >= 0.0 || result != result)
```

`NaN` input: `x < 0.0` is false for `NaN` (comparisons involving
`NaN` are always false), so this falls through to `return x;`,
returning `NaN` itself (the IEEE-754-correct answer — `abs(NaN)` is
conventionally `NaN`). The `ensures` below needs its own `NaN`
escape hatch for that, matching this codebase's established pattern
elsewhere (`sin_f64`/`cos_f64`/`exp_f64`'s own `result != result`
clauses) — an earlier version without it made `abs_f64(NaN)` panic
on its OWN `ensures`, found via `test/fixtures/trig.csv` (TEST-003)
when `exp_f64`'s own double-double machinery produced a `NaN`
intermediate for `+/-Infinity` input and passed it through this
pervasively-used helper.

### `clamp_f64`

```sv0
fn clamp_f64(x: f64, lo: f64, hi: f64) -> f64
    requires(lo <= hi)
    ensures((result >= lo && result <= hi) || result != result)
    ensures(!(lo <= x && x <= hi) || result == x)
```

Clamp x into [lo, hi]. `requires(lo <= hi)` already rules out NaN lo/hi
(every NaN comparison is false, so a NaN operand there fails `lo <= hi`).
NaN x is in-domain and propagates through max_f64/min_f64 as they
document — hence the same `|| result != result` disjunct as min_f64/
max_f64, not present in SPEC.md's literal ARITH-004 wording but required
for the ensures to actually hold on NaN x (this is a spec gap, not a
toolchain one — this library's own contract wording, not filed in
BUGS.md).

### `pow_checked_i64`

```sv0

```

BUGS.md #11 (sv0-mathlib): a `match` used AS A VALUE (`let x: T =
match opt { Some(v) => v, None => dflt };`) declares its own result
temp as plain C `int` regardless of the arms' real type — a match
bound this way silently truncates any i64/u64/f64 arm value, the same
"everything defaults to int" family bug #8 fixed for the payload
BINDING itself, but for the match EXPRESSION's own overall temp
instead. Worked around throughout this function (and everywhere else
in this library from here on) by using `match` as a bare STATEMENT
that assigns into an already-correctly-typed `let mut` local instead
of binding its value directly — confirmed via inspecting the emitted
C that this sidesteps the bug entirely. Not fixed upstream (a real
compiler gap, but a properly general fix needs an emission-time
lookahead/prepass this session ran out of budget for); see BUGS.md
#11 for the full repro and root-cause trace.

### `pow_f64`

```sv0
fn pow_f64(base: f64, exp: f64) -> f64
```

`pow_f64`, per ARITH-007's own wording: `exp_f64(exp * ln_f64(base))`
for `base > 0.0`. `exp_f64`/`ln_f64` are `math::trig`'s R0.2 shared
machinery (this file's own `use trig::...` below is the cross-module
dependency ARITH-007's roadmap step names). Outside `base > 0.0`,
documented IEEE-754-ish behavior (not a full replication of C's `pow`
edge-case table — this library doesn't attempt every negative-base/
non-integer-exponent corner): `base == 0.0` follows the natural
`0^exp` cases (`0` for `exp > 0`, `1` for `exp == 0`, `+Infinity` for
`exp < 0`); `base < 0.0` returns `NaN` unconditionally (a real
simplification versus true IEEE `pow`, which special-cases integer
exponents there — documented, not silently guessed, per GOV-004).

### `pow_i64`

```sv0
fn pow_i64(base: i64, exp: u32) -> i64
    requires(exp < 63 || base == 0 || base == 1 || base == (0 - 1))
    ensures(result == pow_spec(base, exp))
```

Exponentiation by squaring, per SPEC.md Section 14.1's algorithm
sketch (mirrored here almost verbatim). `requires(exp < 63 || ...)`
is deliberately informal (SPEC.md's own wording) — it doesn't rule out
every overflowing `(base, exp)` pair (e.g. `pow_i64(3, 40)` still
overflows silently), only the pathological large-`exp` cases; callers
that can't statically rule out overflow should use `pow_checked_i64`.

### `round_f64`

```sv0
fn round_f64(x: f64) -> f64
    ensures(((result - x) >= (0.0 - 0.5) && (result - x) <= 0.5) || result != result)
```

round-half-away-from-zero (pinned choice, per ARITH-005's requirement
to pin and test one of round-half-to-even / round-half-away-from-zero
explicitly): round(2.5) == 3.0, round(-2.5) == -3.0. Implemented as
floor(x + 0.5) for x >= 0.0 and its negated mirror for x < 0.0 — exact
for every representable x because adding 0.5 to a double is itself
always exact (0.5 == 2^-1, representable with a single mantissa bit
regardless of x's own exponent), so this never introduces a rounding
error the way `(x + BIG) - BIG`-style tricks can.

### `ln_complex`

```sv0
fn ln_complex(c: Complex) -> Complex
    requires(c.re != 0.0 || c.im != 0.0)
```

`ln_complex(c) = ln(|c|) + i*arg(c)` for `c != 0` — undefined (a branch
point) at the origin, per the standard complex logarithm's own domain;
`requires` excludes it the same way `div_complex` excludes `b == 0`.

The real part is deliberately NOT `ln_f64(modulus(c))` — `modulus(c)`
is `hypot_f64(c.re, c.im)`, itself already correctly-rounded to ~1
ULP, but that rounding is a SEPARATE step from the `ln_f64` that
follows it, and near `\|c\| ~= 1` (where `ln\|c\|` itself is near
zero) that extra rounding is enough to blow past this library's own
informational accuracy budget — confirmed via a widened audit sweep:
234 ULP at `c.re ~= -0.694, c.im ~= -0.729` (`\|c\| ~= 1.007`), even
though `ln_f64` and `hypot_f64` each independently measure within 1
ULP on their own. Uses `hypot_f64`'s own overflow-safe scaling
decomposition (`mx`/`mn`/`ratio`) directly against `ln_f64` instead —
`ln\|c\| = ln(mx) + 0.5*ln(1 + ratio^2)` — skipping the intermediate
`sqrt` (and its own rounding) entirely; `ln_f64`'s own accuracy near
`1 + ratio^2 ~= 1` (proven separately in `docs/accuracy.md`) covers
the case `ratio` is small.

### `mul_complex`

```sv0
fn mul_complex(a: Complex, b: Complex) -> Complex
```

── CPLX-003: multiplication/division ────────────────────────────────
`mul_complex` is the standard `(ac - bd, ad + bc)` form, per
CPLX-003's own wording. `div_complex` uses Smith's algorithm (the
conjugate-multiplication form, scaled by whichever of `b.re`/`b.im`
is larger in magnitude) rather than the naive
`(a*conj(b)) / (b.re^2 + b.im^2)` — the naive form squares BOTH
components of `b` unconditionally, which overflows for any `b` whose
magnitude exceeds roughly `sqrt(f64::MAX)`, exactly the same
overflow shape `hypot_f64` (TRIG-007) avoids and CPLX-003 explicitly
cites as the rationale to mirror.

## `random`

deterministic, seedable pseudo-random generator for tests and simulation.

### `below_u64`

```sv0
fn below_u64(state: u64, n: u64) -> BelowU64
    requires(n > 0)
```

Uniform integer in [0, n) with no modulo bias. Divides the u64 range
into `n` equal buckets of width `w = floor(2^64 / n)` and returns the
bucket a raw draw lands in, redrawing when it falls in the leftover
sliver above `n * w` (fewer than `n` values, so the expected number of
draws is below 2). Bucketing by division uses the HIGH bits, which is
what an LCG needs; `draw % n` would use its weak low bits. Requires
`n > 0`.

### `next_u64`

```sv0
fn next_u64(state: u64) -> u64
```

Advances the generator: the returned value is both the next state and
the next raw 64-bit output. Wraps modulo 2^64. Full period (2^64). The
low bits of an LCG are weak, so derive floats from the HIGH bits
(`unit_f64` does).

### `uniform_f64`

```sv0
fn uniform_f64(state: u64, lo: f64, hi: f64) -> f64
    requires(lo <= hi)
    ensures(result >= lo && result <= hi)
```

Uniform f64 in [lo, hi] from one raw generator state (pass the state
returned by `next_u64`). `lo + unit_f64(state) * (hi - lo)`; when the
range is wide relative to `lo`, rounding can land exactly on `hi`, so
the interval is closed at the top. `lo == hi` returns `lo`. `hi - lo`
must be finite: an infinite span returns infinity or NaN.

### `unit_f64`

```sv0
fn unit_f64(state: u64) -> f64
    ensures(result >= 0.0 && result < 1.0)
```

Maps a raw u64 state to an f64 in [0.0, 1.0). Uses the top 53 bits
(`state / 2^11`, exact integer division), which convert to f64 exactly,
then scales by 2^-53 (a power of two, so exact). The result is always
strictly below 1.0; the largest value is 1.0 - 2^-53. Dividing the full
u64 by 2^64 - 1 instead would round the highest states to exactly 1.0.

## `trig`

trigonometry, hyperbolic functions, degree/radian conversion, and (see the deviation note below) sqrt.

### `acos_checked_f64`

```sv0

```

Checked companion to `acos_f64` — None outside [-1.0, 1.0], Some
otherwise.

### `acos_f64`

```sv0
fn acos_f64(x: f64) -> f64
    requires(x >= (0.0 - 1.0) && x <= 1.0)
    ensures(result >= 0.0 && result <= pi_f64())
```

`acos_f64` is deliberately NOT `pi/2 - asin_f64(x)` — near `x ~= 1`,
`asin_f64(x) ~= pi/2`, so that subtraction catastrophically cancels
(confirmed via audit: 3029 ULP near `x ~ 0.99998`, wildly over
PERF-002's 3 ULP budget, versus `asin_f64`'s own well-behaved error
there). Uses the standard half-angle reformulation instead — `acos(x)
= 2*asin(sqrt((1-x)/2))` for `x >= 0`, `acos(x) = pi - 2*asin(sqrt((1+x)/2))`
for `x < 0` — which never subtracts two close-in-magnitude values:
`(1-x)/2`/`(1+x)/2` are each well-conditioned (the SAME well-behaved
shape `asin_f64`'s own `(1.0-x)*(1.0+x)` fix relies on), and reuses
`asin_f64`'s own accuracy directly instead of independently
re-deriving the angle. Non-exact — see docs/accuracy.md's
`acos_f64` row (PERF-002's 3 ULP budget).

### `asin_checked_f64`

```sv0
fn asin_checked_f64(x: f64) -> OptionF64
```

Checked companion to `asin_f64` — None outside [-1.0, 1.0], Some
otherwise.

### `asin_f64`

```sv0
fn asin_f64(x: f64) -> f64
    requires(x >= (0.0 - 1.0) && x <= 1.0)
    ensures(result >= (0.0 - pi_f64()) / 2.0 && result <= pi_f64() / 2.0)
```

── TRIG-003: asin/acos ──────────────────────────────────────────────
`asin_f64` uses `atan(x / sqrt(1 - x^2))` (special-cased at the exact
endpoints `x = 1.0`/`x = -1.0`, where `1 - x^2 == 0.0` would otherwise
divide by zero) — but `1.0 - x*x`, not `(1.0-x)*(1.0+x)`, loses
relative precision near `|x| = 1`: `x*x` rounds to within ~1 ULP of
`x^2`, and subtracting THAT from `1.0` amplifies the absolute rounding
of `x*x` into a much larger RELATIVE error once the result is small
(classic catastrophic cancellation) — confirmed via audit: 12 ULP near
`x ~ -0.99998`, nowhere near PERF-002's 3 ULP budget. `(1.0-x)*(1.0+x)`
computes the same mathematical quantity but each factor is its own
well-conditioned subtraction (no cancellation — `x` isn't close to
`-1`/`1` in a single factor the way `x*x` is close to `1` in the naive
form), so the product retains full relative precision. Non-exact —
see docs/accuracy.md's `asin_f64` row (PERF-002's 3 ULP budget).

### `atan2_f64`

### `atan_f64`


DEVIATION (recorded in README.md): TRIG-004 specifies a STRICT
`result > -pi/2 && result < pi/2` (the true mathematical range of
atan is the open interval). At `f64` precision this is unsatisfiable
for a correctly-rounded implementation: for sufficiently large `|x|`,
`atan(x)` is within less than half a ULP of true `pi/2`, so it rounds
to EXACTLY the nearest representable double to `pi/2` — confirmed
this isn't a bug specific to this library by checking the system libm
directly (`atan(1e50)`, `atan(1e300)`, etc. all return bit-identical
`1.5707963267948966`, `== M_PI/2`, in plain C). Tightening this
function further (as this file's own accuracy work just did) makes
hitting that boundary MORE likely, not less — an earlier, less
accurate version of this function happened to round just short of the
boundary by coincidence, masking the same underlying issue. The
`ensures` below uses `>=`/`<=` instead, matching `sin_f64`/`cos_f64`'s
own boundary-inclusive convention. Non-exact — see
docs/accuracy.md's `atan_f64` row (PERF-002's 2 ULP budget).


── TRIG-005: hyperbolic forms ───────────────────────────────────────
`sinh_f64` near zero: the naive `(exp(x) - exp(-x)) / 2` form
catastrophically cancels for small `|x|` (`exp(x)` and `exp(-x)` are
both near `1.0`, so their difference loses most of its significant
digits before the subtraction even happens) — so for `|x| < 1.0` this
uses `sinh`'s own Taylor series instead (`x + x^3/3! + x^5/5! + ...`,
no cancellation, converges to well past double precision in 15 terms
given `|x| < 1.0`), falling back to the `exp_f64`-based form only once
`exp(x)` genuinely dominates `exp(-x)` and cancellation isn't a
concern.

`tanh_f64` for large `|x|`: `exp_f64(2x)` overflows to `Infinity` well
before `tanh(x)` itself would ever meaningfully differ from its
asymptote (`tanh(20.0)` already differs from `1.0` by less than
`1e-17`, past `f64` precision) — clamped explicitly rather than
letting `(Infinity - 1) / (Infinity + 1)` produce `NaN`.
Non-exact — see docs/accuracy.md's `sinh_f64`/`cosh_f64`/`tanh_f64`
rows (informational 3 ULP budgets).

### `sqrt_f64`

```sv0

    requires(x >= 0.0)
```

`+Infinity` is a real, in-domain input (`requires(x >= 0.0)` doesn't

Bracket-then-Newton with `x = Infinity`: `sqrt_bracket_guess` doubles
`guess` until `guess*guess > x`, but `guess*guess` itself overflows to
`Infinity` long before that (`Infinity <= Infinity` stays true), so
the bracket loop only stops at its own 1100-iteration safety cap,
returning some enormous-but-finite guess; the Newton loop then
computes `x / guess = Infinity / finite = Infinity` on its first
iteration, then `Infinity / Infinity = NaN` on the very next one —
`sqrt_f64(Infinity)` was silently returning `NaN`, not `Infinity`,
and `NaN >= 0.0`/`abs_f64(NaN - x) <= ...` both being false made the
`ensures` panic rather than silently propagate the wrong answer,
which is how this was caught. Non-exact — see docs/accuracy.md's
`sqrt_f64` row (PERF-002's 2 ULP budget).

### `tan_f64`

```sv0
fn tan_f64(x: f64) -> f64
```

TRIG-002: `tan_f64(x)` is `sin_f64(x) / cos_f64(x)` — deliberately
WITHOUT a `requires` excluding the asymptote (`cos_f64(x) == 0.0`):
TRIG-002's own wording notes a `requires` there isn't practical (the
domain is dense reals, no input is "statically known" to hit the
asymptote), so `tan_f64` is instead a total function, returning
`Infinity`/`-Infinity`/`NaN` at the asymptote per ordinary IEEE-754
division semantics — the CONV-005(b) path (documented propagation),
not 5(a) (a `requires`/`_checked` pair). `tan_checked_f64` is kept
anyway for API consistency with every other domain-adjacent function
in this module, even though TRIG-002 doesn't require it (`cos_f64(x)
== 0.0` is itself the only "domain violation," already handled by the
unchecked form's own IEEE-754 behavior). Non-exact — see
docs/accuracy.md's `tan_f64` row (PERF-002's 2 ULP budget).

### `tanh_f64`

```sv0
fn tanh_f64(x: f64) -> f64
    ensures(result > (0.0 - 1.0) && result < 1.0)
```

`tanh_f64`'s clamp branches return the nearest double STRICTLY inside
`(-1.0, 1.0)` (`0.9999999999999999`, one ULP below `1.0` — the
largest double `< 1.0`), not literally `1.0`/`-1.0`. Mathematically
`tanh(20.0)` is already indistinguishable from `1.0` at double
precision (differs by under `1e-17`), so `1.0` itself would be the
more numerically "honest" rounding — but TRIG-005's own `ensures`
demands a STRICT bound, so this favors satisfying the contract as
written over that extra, unobservable-at-this-precision honesty.

The `|x| > 20.0` pre-clamp alone is NOT sufficient — found via a
widened accuracy-audit sweep ([-50,50], not just near the original
clamp boundary) that `exp_f64(2*x)` underflows enough for
`(e2x-1)/(e2x+1)` to round to exactly `+/-1.0` starting around `|x| ~=
19.98`, a real `ensures` panic ("sv0 contract violation: ensures
failed in tanh_f64") for input as unremarkable as `x = -19.999`. Kept
the pre-clamp anyway (it's still needed: without it, `x` large enough
that `exp_f64(2*x)` itself overflows to `Infinity` computes
`(Infinity-1)/(Infinity+1) = Infinity/Infinity = NaN`, a DIFFERENT
failure mode entirely) and ADDED a post-hoc check on the actual
computed `t` for the narrower gap the pre-clamp's threshold doesn't
quite reach — belt-and-suspenders, since the post-hoc check alone
(were the pre-clamp removed) would let large-`x` inputs reach the
`Infinity/Infinity` `NaN` case before ever getting a chance to clamp.

`|x| < 1.0` ALSO needed its own fix, same shape as `sinh_f64`'s own
near-zero branch above: `exp_f64(2*x)` near `x = 0` is close to
`1.0`, so `e2x - 1.0` catastrophically cancels — found via the same
widened sweep, 121 ULP against a 3 ULP informational budget at `x ~=
0.001`. Delegates to `sinh_f64(x) / cosh_f64(x)` there instead:
`sinh_f64` already has its own cancellation-free Taylor branch for
`|x| < 1.0` (see above), and `cosh_f64` near zero has no cancellation
to begin with (`exp(x) + exp(-x)` near `2.0`, nothing subtracts).
Non-exact — see docs/accuracy.md's `tanh_f64` row (informational 3
ULP budget).
